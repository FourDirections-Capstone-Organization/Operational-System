2. Verify Each Component

2.1 PostgreSQL — CDC Publication

Command:

docker compose exec db psql -U postgres -d backend_db -c "\dRp+"

Expected output:

Publication stars_cdc Owner | All tables | Inserts | Updates | Deletes | Truncates ----------+------------+---------+---------+---------+---------- postgres | t | t | t | t | t

Why this matters: All tables = t means every INSERT, UPDATE, and DELETE on any table in the database will be published. Debezium will read this publication and convert each change into a JSON event in Kafka.

2.2 Kafka — Running and Responding

Command:

docker compose exec kafka /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 --list

Expected output: (empty — no topics yet, which is expected)

An empty list is correct. No topics exist because no one has published any messages yet. Once Debezium is configured in Step 3, topics will appear here automatically.

To test manually: If you want to see Kafka respond with more than an empty list, run this instead:

docker compose exec kafka /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 --describe

This should return metadata about the cluster without error — confirming Kafka is alive.

2.3 Debezium — REST API

Command:

curl http://localhost:8083

Expected output (example):

{"version":"3.9.4","commit":"...","cluster_id":"...","server":"..."}

Why this matters: Debezium runs as a Kafka Connect worker. Port 8083 is its REST API. You send HTTP requests here to register a connector (which we will do in Step 3). A JSON response means Debezium is listening.

Bonus check — list connectors (should be empty):

curl http://localhost:8083/connectors

Expected: [] (empty array — no connectors registered yet).

4. Build and Run Everything from Scratch

This section covers every scenario for starting the project and rebuilding it after changes.

ScenarioCommandWhat happens
First time rundocker compose up -dPulls all images from Docker Hub (PostgreSQL, Neo4j, Kafka, Debezium). Builds the backend (.NET restore + publish) and frontend (npm ci + vite build). Then starts all six containers.
After cleanup (data preserved)docker compose up -dReuses cached images and builds. Starts all containers. Data from the previous session is intact.
After full wipedocker compose up -dCreates fresh volumes (PostgreSQL runs init script again, creates publication). Neo4j creates a new empty database. Kafka starts with no topics.
After code changes (rebuild)docker compose up -d --buildForces backend and frontend to rebuild from source. Use this if you changed C# or TypeScript code.
Start only specific servicesdocker compose up db neo4j -dStarts only PostgreSQL and Neo4j. Useful if you just want to test those without the full stack.
Resume after stopdocker compose startStarts existing containers without recreating them. Faster than up.

What happens step by step when you run docker compose up -d

  1. Images are pulled (first time only): postgres:16-alpine, neo4j:latest, apache/kafka:latest, quay.io/debezium/connect:latest
  2. Backend is built: dotnet restore + dotnet publish inside the Docker build stage
  3. Frontend is built: npm ci + npm run build (vite) inside the Docker build stage
  4. Volumes are created: pgdata, kafka-data, neo4j-data/ folder
  5. Containers start in order:
    1. postgres starts and becomes healthy (init script creates publication)
    2. neo4j starts and becomes healthy
    3. kafka starts and becomes healthy (KRaft mode, no ZooKeeper)
    4. backend starts after PostgreSQL is healthy (applies EF migrations + seeds data)
    5. frontend starts after backend is up
    6. debezium starts after both PostgreSQL and Kafka are healthy

Tip — first time build takes a few minutes because Docker needs to download SDK images (mcr.microsoft.com/dotnet/sdk:9.0 is ~1.5 GB). Subsequent runs are faster because everything is cached.

Note about the JWT_KEY warning: You might see The "JWT_KEY" variable is not set when running any compose command. This is harmless — the backend uses a default secret key from appsettings.json during development. To suppress the warning, create a .env file in the project root:

JWT_KEY=YourSuperSecretKeyAtLeast32CharactersLong!ChangeThisInProduction

5. Cleanup Options

Depending on what you need, choose one of these:

Stop everything (keep data for next session)

docker compose stop

Stops all containers. Run docker compose start later to resume. All data in PostgreSQL, Kafka, and Neo4j is preserved.

Stop and remove containers (keep data)

docker compose down

Containers and the Docker network are removed. Volumes (pgdata, kafka-data, neo4j-data/) are kept. Run docker compose up -d to recreate containers with all data intact.

Full wipe (delete all data, start fresh)

docker compose down -v Remove-Item -Recurse -Force neo4j-data

The -v flag deletes the named volumes (pgdata, kafka-data), wiping PostgreSQL and Kafka data. The neo4j-data/ folder is deleted manually since it is a bind mount (not a named volume). Run docker compose up -d to start fresh with empty databases.

Note about your current state: All six services are currently running. I did not clean up after verifying them — you are still in a "running" state. If you want to leave them running for later, you can just close your terminal. If you want to stop them now, use one of the cleanup options above.
