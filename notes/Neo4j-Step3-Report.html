1. What We Were Trying to Do

Step 3's goal was to register the Debezium PostgreSQL connector — a single HTTP request that tells Debezium: "Connect to PostgreSQL and start publishing every row change to Kafka."

Once registered, the pipeline should look like this:

PostgreSQL → (WAL changes) → Debezium → (JSON events) → Kafka Topics

Every INSERT, UPDATE, or DELETE in PostgreSQL would instantly appear as a JSON message in a Kafka topic named stars.public.<TableName>.

2. What Actually Happened — Three Problems

1 PowerShell vs. JSON quoting

Error: 500 "Unexpected character ('n') ... CreateConnectorRequest is null"

When I tried to send the registration request using docker compose exec debezium curl ... -d '{...}', the JSON got mangled because PowerShell's quoting rules are different from Linux shells.

What happened to the JSON:

What I intendedWhat arrived inside the container
{"name":"stars-..."}{name:stars-...} (all quotes stripped)

Without the quotes, the Java JSON parser couldn't deserialize the request, so the createRequest object was null.

Fix: Instead of embedding JSON in the command, I wrote the JSON to a file on the host using PowerShell's Set-Content, then copied it into the container with docker cp. This preserved all the quotes correctly.

2 Debezium 3.6 renamed a required config field

Error: 400 "The 'topic.prefix' value is invalid: A value is required"

After fixing the quoting, the connector config was valid JSON but still rejected. The error pointed to topic.prefix.

Root cause: In Debezium version 3.6 (the version in the image we pulled), the configuration field database.server.name was renamed to topic.prefix. The old name is silently ignored. Our config file still had database.server.name: stars, so the required topic.prefix was missing.

Old config (worked in older versions)New config (required by v3.6)
"database.server.name": "stars""topic.prefix": "stars"

Fix: Changed the config to use topic.prefix instead of database.server.name.

3 Kafka replicated 3 copies — but there is only 1 broker

Error: 500 "Request timed out. The worker is currently ensuring membership in the cluster"

This was the hardest problem. Every registration request took exactly 90 seconds and then returned 500 with a "cluster membership" error. The Debezium (Kafka Connect) worker was stuck in an infinite rebalance loop.

Root cause — a single line in the Kafka logs gave it away:

WARN Auto topic creation failed for __consumer_offsets with error 'INVALID_REPLICATION_FACTOR': Unable to replicate the partition 3 time(s): The target replication factor of 3 cannot be reached because only 1 broker(s) are registered

Here is what that means in plain language:

  • Kafka stores consumer group metadata (which consumer is reading what) in an internal topic called __consumer_offsets
  • By default, Kafka tries to create this topic with 3 copies (replication factor 3) so if one copy fails, another takes over
  • But we are running only 1 Kafka broker — there is only one machine to hold copies
  • Kafka could not create the topic because it needed 3 places to store it, but only 1 existed
  • Without that topic, the Debezium consumer group could never establish membership, so it kept trying and failing in a loop

Analogy: Imagine a library that only has 1 shelf, but the system says "you must store each book on 3 different shelves." The system keeps trying and failing forever.

Fix: Added one environment variable to Kafka:

KAFKA_OFFSETS_TOPIC_REPLICATION_FACTOR: 1

This tells Kafka: "It is OK to store only 1 copy since we only have 1 broker."

I also added two related variables:

KAFKA_TRANSACTION_STATE_LOG_REPLICATION_FACTOR: 1 KAFKA_TRANSACTION_STATE_LOG_MIN_ISR: 1

These prevent the same issue from happening with transactional topics.

5. The Final Verification

After fixing all three issues, the connector was registered and an end-to-end test confirmed CDC is working:

1. PostgreSQL: UPDATE Users SET FirstName = 'CDC-Test-Updated' WHERE EmployeeNumber = 'MGR001'; ↓ 2. WAL (Write-Ahead Log) captures the row diff ↓ 3. Debezium reads the WAL and formats as JSON ↓ 4. Kafka topic stars.public.Users receives a message ↓ 5. Verified by consuming the message with kafka-console-consumer

The JSON message contained:

  • "op": "r" — operation type (r = snapshot read, c = create, u = update, d = delete)
  • "after": { ... } — the full row data after the change
  • "before": null — the previous state (null because this was a snapshot)
  • "source": { "table": "Users", "db": "backend_db", ... } — metadata about the change

Kafka topics created automatically by Debezium:

__consumer_offsets (Kafka internal) __debezium-heartbeat.stars (Debezium keep-alive) stars-connect-configs (Kafka Connect internal) stars-connect-offsets (Kafka Connect internal — tracks which WAL position was read) stars-connect-statuses (Kafka Connect internal) stars.public.Departments (CDC data) stars.public.JobPositions (CDC data) stars.public.NotificationSettings (CDC data) stars.public.Users (CDC data — verified with test update)

7. What We Learned

  • PowerShell and inline JSON do not mix well. The @ sign for curl's -d @filename is treated as a PowerShell operator. Always write JSON to a file first and use docker cp to transfer it.
  • Single-broker Kafka needs explicit replication factor configuration. Without KAFKA_OFFSETS_TOPIC_REPLICATION_FACTOR=1, consumer groups cannot form and the cluster appears stuck.
  • Always check the companion service's logs. The Debezium error pointed to "cluster membership", but the real cause was in Kafka's logs (INVALID_REPLICATION_FACTOR). The symptom and the cause were in different containers.
  • Tool versions matter. Debezium 3.6 renamed a config field (database.server.name → topic.prefix) which is not backward compatible.
