Architecture decisions, data model, pipeline design, and suitability scoring for task-employee matching using Change Data Capture with Neo4j

Graph DB: Neo4j

1. Change Data Capture (CDC) — What and Why

Change Data Capture (CDC) is a pattern that tracks changes (INSERT, UPDATE, DELETE) happening in a database and streams those changes to other systems. Instead of the application manually emitting events, CDC listens to the database's internal transaction log and captures every change automatically.

Why CDC instead of application-level events?

  • Zero code changes to the existing STARS backend — no new event emitters, no refactoring
  • Complete coverage — even direct database updates (e.g., a DBA correcting a record) are captured
  • Decoupling — the suitability engine is independent of the operational system. It can fail, restart, or be upgraded without affecting STARS
  • Audit completeness — every change to Tasks, Users, Assignments, and Recommendations lands in the CDC stream
Note: STARS already has an AuditLog table that records changes. However, CDC captures the raw row-level diffs (old values vs. new values), which is more granular and includes data the application code might not explicitly log.

2. Database-Level CDC — PostgreSQL Logical Replication

PostgreSQL has a built-in feature called Logical Replication. It works as follows:

  1. Every change to a table is written to the Write-Ahead Log (WAL) — PostgreSQL's internal journal
  2. A publication defines which tables to watch
  3. A replication slot ensures changes are preserved until consumed
  4. The output plugin (pgoutput) decodes WAL entries into JSON format

Sample CDC JSON event produced by PostgreSQL logical replication:

{ "op": "u", "table": "Tasks", "before": { "Status": "InProgress", "UpdatedAt": "2026-07-14T10:00:00Z", "AssignedUserId": "user-001" }, "after": { "Status": "Completed", "UpdatedAt": "2026-07-15T10:30:00Z", "AssignedUserId": "user-001" }, "source": { "ts_ms": 1721040000000, "table": "Tasks" } }

Tables to include in the publication:

TableWhy CaptureChange Frequency
TasksTask lifecycle: status changes, deadline changes, priority changes, reassignmentsHigh
TaskAssignmentsWho is assigned to what — used for workload calculation and experience trackingHigh
UsersAvailability status (Active/Offline/OnLeave), role, department changesLow
RecommendationsPerformance feedback from coordinators — the core of suitability scoringMedium
DepartmentsDepartment structure changesVery Low

SQL to create the publication:

CREATE PUBLICATION stars_cdc FOR TABLE "Tasks", "TaskAssignments", "Users", "Recommendations", "Departments";

3. Why Neo4j Over PostgreSQL for This Use Case

The suitability engine is fundamentally a graph traversal problem. We need to answer questions like:

  • "Which employees in this department have completed similar tasks before?"
  • "Who has the best recommendation history and lowest current workload?"
  • "Who has worked with this coordinator before?"
FactorPostgreSQL (Relational)Neo4j (Graph)
Finding relationshipsRequires multiple JOINs across 4-5 tables. Performance degrades as data grows.Relationships are stored as direct pointers. Traversal is O(1) per hop regardless of data size.
Variable-depth queriesRequires recursive CTEs — complex, hard to read, slow at scale.Cypher's MATCH (e)-[:ASSIGNED_TO*1..5]->(t) traverses intuitively.
Weighted scoringNeeds subqueries, window functions, and complex aggregation.Pattern matching + aggregation in a single readable query.
Schema flexibilityAdding new relationship types requires new junction tables, migrations, joins.Just add a new relationship type — no schema migration needed.
ReadabilitySQL for multi-hop path queries becomes long and nested.Cypher uses ASCII-art patterns — the query visually resembles the graph structure.
When PostgreSQL is still better: PostgreSQL remains the source of truth for all operational data. Neo4j is a purpose-built cache for graph traversal queries. We do not replace PostgreSQL — we complement it.

4. Derived Insights vs. Read-Only Mirror

We chose the Derived Insights approach. Here is what each term means and why it matters:

Read-Only Mirror (not chosen)

Every row in PostgreSQL has a corresponding node in Neo4j. Raw data is copied 1:1. Neo4j is a direct replica but in graph form.

  • ✅ Simple to implement
  • ❌ Stores every row — wasted space in Neo4j
  • ❌ The query still has to aggregate/calculate at read time
  • ❌ Does not take advantage of Neo4j's ability to store pre-computed values

Derived Insights (chosen)

The CDC processor reads raw events, computes summaries and aggregates, and stores only the derived values into Neo4j.

  • ✅ Neo4j stores compact, query-ready data — fast reads
  • ✅ Pre-computed scores and aggregates — no heavy computation at query time
  • ✅ Full history remains in PostgreSQL; Neo4j is purely analytical
  • ❌ Slightly more complex CDC processor logic
  • ✅ Can be rebuilt from scratch by replaying CDC events

Concrete example:

Instead of storing every Recommendation row as a node, the CDC processor computes:

Employee.avgTimelinessScore = 0.92 // 92% of Timeliness recommendations are positive Employee.avgWorkQualityScore = 0.88 // 88% of WorkQuality recommendations are positive Employee.workload = 3 // Currently assigned to 3 active tasks Employee.completedRoutineTasks = 15 // Has completed 15 Routine tasks historically

These are stored as properties on the :Employee node, not as separate nodes.

6. Suitability Scoring System

The suitability score determines which employee is the best fit for a given task. It is a weighted composite score calculated in the Cypher query at read time (not stored), based on the derived properties stored on the :Employee node.

Scoring Factors

FactorWeightSourceDescription
Workload Balance35%Employee.workloadEmployees with fewer active tasks score higher. Lower is better.
Experience Match25%Employee.completedRoutineTasks or completedSpecialTasksEmployees who have completed more tasks of the same classification score higher. Higher is better.
Recommendation Score40%avgTimelinessScore, avgWorkQualityScore, avgCommunicationScoreEmployees with higher average recommendation scores across categories score higher. Higher is better.

Additional filters applied before scoring (hard cutoffs):

  • Employee must be in the correct department (task's AssignedDepartmentId)
  • Employee must have availabilityStatus = "Active"
  • Employee must have a role eligible for this task (e.g., Dispatcher, Courier, Encoder depending on task type)

Cypher Query — Suitability Ranking

MATCH (d:Department {id: $departmentId}) MATCH (e:Employee)-[:BELONGS_TO]->(d) WHERE e.availabilityStatus = "Active" AND e.role IN $eligibleRoles WITH e, 1.0 - (e.workload * 1.0 / $maxWorkload) AS workloadFactor, CASE WHEN $taskClassification = "RoutineDailyTask" THEN e.completedRoutineTasks * 1.0 / $maxRoutineXP ELSE e.completedSpecialTasks * 1.0 / $maxSpecialXP END AS experienceFactor, (e.avgTimelinessScore + e.avgWorkQualityScore + e.avgCommunicationScore) / 3.0 AS recScore RETURN e.employeeNumber, e.firstName + " " + e.lastName AS name, e.role, e.workload, (0.35 * workloadFactor + 0.25 * experienceFactor + 0.40 * recScore) AS suitabilityScore ORDER BY suitabilityScore DESC LIMIT 5

Weights (0.35, 0.25, 0.40) are configurable and should be tuned over time based on business priorities.

8. Data Flow — Step by Step

  1. Change occurs in PostgreSQL — a coordinator assigns a task, an employee's availability changes, a recommendation is submitted
  2. WAL captures the change — PostgreSQL writes the diff to its internal transaction log
  3. Debezium reads the WAL — the Debezium connector polls the replication slot and converts the row change into a JSON event
  4. Event lands in Kafka — the JSON event is published to the stars.cdc Kafka topic
  5. CDC Processor consumes the batch — every 10 minutes (or on demand), the processor reads new events from Kafka
  6. Derived insights are computed:
    • Recalculate workload counts from TaskAssignment events
    • Recalculate recommendation averages from new Recommendation events
    • Update availability status from User events
    • Update experience counts from completed Task events
  7. Neo4j is updated — using MERGE to create or update nodes and relationships, the processor writes the derived data
  8. Coordinator/Manager queries — the STARS UI calls the suitability API, which runs the Cypher query and returns the top 5 candidates with scores
  9. Assignment decision — the coordinator or manager picks an employee and assigns the task in STARS
  10. CDC cycle repeats — the assignment change triggers another CDC event, closing the loop

9. Reciprocity: What Changes Flow Back?

A critical architectural decision: Neo4j is read-only from the application's perspective.

  • PostgreSQL → Neo4j: Unidirectional. CDC events flow one way.
  • No writes from Neo4j to PostgreSQL. The operational system never reads from Neo4j for writes.
  • The suitability API is a read-only advisory endpoint. It suggests employees but does not assign them. The actual assignment happens back in STARS, which creates a new CDC event, which updates Neo4j.

This ensures data integrity. PostgreSQL remains the single source of truth. Neo4j is always rebuildable from scratch by replaying CDC events.
